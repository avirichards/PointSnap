# Agent 4 — Mobile API mapping for 28 airline targets

Date: 2026-05-19
Researcher: Claude Code (read-only research; no MITM performed)

## Method

For each airline I:
1. Ran WebSearch on `<airline> mobile API`, `<airline> Charles proxy intercept`, `<airline> iOS app reverse engineer`, `<airline> NDC API`, plus targeted hostname searches.
2. Probed candidate mobile / API hostnames with `curl -I` (HEAD), 6-second timeout, default UA. Captured HTTP status, CDN/WAF fingerprints (`server`, `akamai-grn`, Cloudflare challenge HTML, AWS API Gateway error shape, etc.) and `Set-Cookie` headers (`_abck`, `bm_sz` → Akamai BMP; `cf_chl_*` → Cloudflare; `__Host-px*` → PerimeterX; `AWSALB` → AWS ALB).
3. Looked for the specific iOS/Android `mobile.*` or `api.*` subdomain referenced in public writeups (LinkedIn, GitHub, dev.to, Medium, IAG / Lufthansa / Finnair / AC NDC developer portals).
4. Cross-checked the existing PointSnap `tasks/scraper-log.md` — the AA observation that `mobile.aa.com` returns "200/76KB while www.aa.com is Akamai-blocked" was the reference point for what "viable mobile path" looks like.

Caveats: I did NOT decompile any APK / IPA, did NOT MITM any device, did NOT bypass cert pinning. All endpoint identification here is from public writeups + edge-server fingerprints reachable without auth. Cert-pinning columns are best-effort based on (a) known industry practice for the carrier's app vendor stack, (b) absence of a public bypass writeup (which usually surfaces when pinning is loose), (c) presence of Akamai BMP SDK signals in their web surface (carriers running BMP web-side almost always pin in-app). All such inferences are flagged.

## Synthesis 1 — Top 5 airlines where the mobile path is most promising as a T6 transport tier

1. **Qantas (api.qantas.com)** — strongest signal of the entire set. Their API gateway returns full reference data with **no auth at all** (3.9 MB JSON of every airport, world-wide, on a single GET). Tiered protection means the booking/availability endpoints probably need a QFF Bearer JWT but the API gateway is **not** Akamai-fronted in default-deny mode the way every other carrier's is. Worth (a) capturing the Qantas iOS/Android app's auth flow to mint a JWT, (b) probing the `flight/*` and `loyalty/*` subtrees, (c) confirming whether `availability` requires only Bearer or also a per-device fingerprint. **Recommended T6 priority #1.**
2. **American Airlines (api.aa.com + mobile.aa.com)** — `api.aa.com/` is an **HTTP/2 API gateway with CORS for `x-api-key` and `authorization` headers, `Cache-Control: no-store`** — exactly the shape of a mobile-app API gateway. Combined with the existing scraper-log observation that `mobile.aa.com` returns 200/76KB to the right UA, AA is the strongest North American candidate. Open question: is the `x-api-key` baked into the iOS IPA / Android APK as a static-but-rotated string, or minted per session? Worth one read-only static-string scan of the publicly downloadable Android APK from APK mirror to find a candidate key, then probe `api.aa.com/v1/...` paths with it (the 405s indicate the paths are alive but want POST). **Recommended T6 priority #2.**
3. **JetBlue (managetrips.jetblue.com /api/graphql)** — JetBlue's mobile and web both speak GraphQL at a documented path. GraphQL is far easier to map than REST because the schema can sometimes be introspected, and JetBlue is not a known Akamai BMP customer. The existing dev-portal QA host (`developerqa.jetblue.com/io-docs`) leaks operation names. Worth confirming whether introspection is enabled and what the award-availability operation name is. **Recommended T6 priority #3.**
4. **Alaska Airlines (api.alaskaair.net)** — Alaska published their own iOS networking library (`atom`) on GitHub, including the production OAuth2 endpoint URL. The fact that Alaska open-sourced their network library at all is a strong cultural signal that their app stack is less hostile than UA / DL / AA. The host doesn't resolve from this sandbox (likely VPN/geo-fenced), but from a US mobile network it should reach. **Recommended T6 priority #4.**
5. **British Airways (api.ba.com/rest-v1/)** — IAG has a fully published REST API base URL + matrix-parameter filter spec on their developer portal, including consumer-grade endpoints like `/v1/flights`. Partner key registration is open. The TLS-reset behavior observed on `api.ba.com/` to a default curl UA is likely a TLS fingerprint check, not a fundamental block — defeated by sending a realistic Chrome / iOS Safari TLS handshake. **Recommended T6 priority #5.**

Honorable mentions (close to the top 5 but with caveats):
- **VoeGol / Gol (b2c.voegol.com.br + api.smiles.com.br)** — fully reachable B2C SPA, no aggressive bot defense observed; almost certainly a viable mobile path but the API surface is currently undocumented publicly. Worth one DevTools network capture session against the b2c SPA to find the actual endpoints.
- **Finnair (m.finnair.com)** — does a clean 302 with no bot-defense cookies on the redirect. The cleanest mobile redirect of the entire set. Probably easy to walk into.

## Synthesis 2 — Airlines where mobile is unlikely to help (mobile API is as defended as web)

These all show Akamai BMP / PerimeterX / Cloudflare Turnstile signals on their `api.*` or `mobile.*` host, AND have no public bypass writeup, AND have a verified track record of aggressive bot defense:

- **Air Canada (api.aircanada.com)** — AWS APIGW + the `mobile.aircanada.com` 404 page inlines Akamai sensor.js. App is almost certainly Akamai-BMP-pinned. The fact that even the 404 carries the sensor is a tell. Match the existing scraper-log observation that Aeroplan is the hardest to crack.
- **Delta (mobile.delta.com, api.delta.com)** — `mobile.delta.com` 503, `api.delta.com` redirects to www which serves an Akamai 403 page with reference id. Same Akamai BMP stack as the web. No softer mobile path.
- **Lufthansa Miles & More (api.miles-and-more.com)** — confirmed **Cloudflare Turnstile** challenge HTML on the API host. M&M consumer app sits behind Cloudflare bot defense; bypassing CF Turnstile is the same problem as bypassing it on web.
- **Singapore Airlines (api.singaporeair.com)** — Akamai-grn header, classic Edge reject. SQ is an Akamai BMP customer per Fork.ai. Mobile path is not softer.
- **LifeMiles (api.lifemiles.com)** — Akamai-grn header, classic Edge reject. Same story.
- **Saudia (api.saudia.com)** — **PerimeterX** behavioral challenge. PX is reasonably tractable for stateless GETs but a stateful flow (login → JWT → search) on PX is hard. No softer mobile path.
- **Emirates (mobile.emirates.com)** — Akamai BMP cookies present (`_abck`, `bm_sz`) on the mobile site itself. AWS-fronted underneath. Same defenses as web.
- **Virgin Atlantic (m.virginatlantic.com)** — Akamai BMP cookies on first request. Mobile path no better than web.

Carriers where mobile API base URL could not be enumerated and there's no public writeup (so the realistic plan is to capture from the actual app, which is out of scope for read-only research): **Etihad, SAS, Qatar Airways, Aeromexico, Virgin Australia, ANA, Turkish Airlines** (last two have hosts that exist in DNS but don't reach from US edge — likely geo-fenced; would need a Singapore / Tokyo / Istanbul egress to even probe). For these, the mobile angle requires either (a) a paid mobile-API-mapping service or (b) actually capturing the app traffic with a dev device and Frida, neither of which is in scope here.
